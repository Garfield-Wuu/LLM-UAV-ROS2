## 4.2 任务理解层实现逻辑

### 4.2.1 LLM 部署与 API 调用机制

任务理解层通过 `llm_client.py` 节点实现，支持**双后端透明切换**（代码第 225–248 行）：

**Groq Cloud 后端**（`_call_groq`，第 639–669 行）：
- 可选模型：`llama-3.3-70b-versatile`（综合最优，推荐用于复杂多步规划）、`llama-3.1-8b-instant`（极速响应，适合简单控制指令）、`mixtral-8x7b-32768`（混合专家长上下文推理）、`gemma2-9b-it`（轻量高效）。
- 使用纯标准库 `urllib.request` 发起 HTTPS POST 请求至 `https://api.groq.com/openai/v1/chat/completions`，**零额外依赖**，支持离线 Ollama 场景。
- 关键参数：`temperature=0.1`（趋近确定性输出）、`max_tokens=500`、`response_format: {"type": "json_object"}`（强制纯 JSON 输出，消除幻觉解释文字）。

**Ollama 本地后端**（`_call_ollama`，第 671–693 行）：
- 可选模型：`qwen2.5:7b`（通义千问，中文优化）、`deepseek-r1:7b`（推理增强，带 `<think>` 推理块）、`qwen3-coder:30b`（复杂规划首选）、`mistral:7b`（通用推理）。
- 请求发至本地 `http://localhost:11434/api/chat`（可通过 `ANTHROPIC_BASE_URL` 环境变量重定向至远程 Ollama 网关）。
- 关键参数：`format: "json"`（Ollama 原生 JSON 模式）、`stream: false`、`temperature: 0.1`。
- **冷启动预热**：Ollama 大模型首次加载需将权重从磁盘加载至 VRAM（可能需要 10–60 秒），节点启动时在后台线程执行 `_warmup_ollama()`，配合动态 spinner 进度条，预热完成前不开放用户输入，避免首条指令因超时白费。

**线程模型**：LLM 推理在 `ThreadPoolExecutor(max_workers=1)` 线程池内执行，与 ROS 2 spin 线程完全隔离，序列化执行（防止并发重叠请求），超时上限 `llm_timeout_sec=120 s`（兼顾远程 Ollama + 大模型 + 长飞控 Prompt 的极端场景）。

### 4.2.2 鲁棒 JSON 提取算法——五步容错解析流程

生成式模型输出具有不确定性（可能夹带 Markdown 代码块、推理文字、`<think>` 块等），`_extract_json_robust()` 方法（第 799–843 行）实现了五步容错解析：

**第一步：预处理（Strip & Clean）**  
`_strip_fences()` 移除 Markdown 代码围栏（` ```json...``` `）和 `<think>...</think>` 推理块。推理块内容由 `_extract_think()` 单独提取，持久化写入 ROS 2 日志文件（`~/.ros/log/`）供可解释性分析，同时在终端打印单行摘要（字符数/行数/首行预览），不打断对话流。

**第二步：正则定位（Balanced Brace Extraction）**  
`_balanced_json_candidates()` 通过单次线性扫描识别所有顶层括号平衡的 `{...}` 子串（正确处理任意深度嵌套），并按**长度降序**排列候选结果（越长的候选通常包含越完整的上下文）。

**第三步：标准解析（Cascaded Parse Attempts）**  
按以下三个子策略顺序尝试，首个成功即返回：
- **S1**：对预处理后的完整文本直接调用 `json.loads()`；
- **S2**：遍历括号平衡候选集，每个候选调用 `json.loads()`，要求结果包含 `action` 或 `plan` 键；
- **S3**：正则回退，匹配 `{"action":"...", ...}` 单步指令模式和 `{"plan":[...]}` 计划模式两类正则表达式（`re.DOTALL` 跨行匹配）。

**第四步：字段校验（Schema Validation & Type Coercion）**  
`_parse_and_validate()` 执行严格校验序列（第 880–939 行）：
1. 动作名规范化（`_normalize_action`）：将 36 个别名（如 `FIND`/`SEARCH`/`LOCATE`/`GOTO`/`NAVIGATE`）映射到 12 个规范动作名；
2. 白名单拦截（`ALLOWED_ACTIONS`）：任何不在白名单中的动作直接拦截；
3. 类型强制转换（`_coerce_params`）：按 `_PARAM_SCHEMA` 中每个动作的参数定义，执行 `type_fn(v)` 类型转换和 `max(lo, min(hi, v))` 区间截断；
4. 高度/速度硬限：altitude ≤ 120 m，水平速度 ≤ 15 m/s（保护层，独立于 LLM）。

**第五步：安全兜底（Safety Fallback to HOVER）**  
以下任意情形触发回退至 `HOVER`（零速悬停指令）：
- 动作名不在白名单；
- `FIND_AND_GOTO` 的 `query` 字段为空字符串；
- 三步解析全部失败（`_extract_json_robust` 返回 `None`）；
- 自动起飞注入：若无人机处于地面状态（`flight_phase == 'GROUND'`）且收到飞行指令，自动在输入队列头部插入 `TAKEOFF`，原指令延后执行。

### 4.2.3 提示工程——任务原语 Schema 定义

系统提示词（`_SYSTEM_PROMPT_TEMPLATE`，第 162–209 行）采用**结构化分块式模板**，包含五个功能区：

**① 任务原语 Schema 区（核心）**：以枚举表格形式定义全部 12 个合法动作原语，每条给出完整 JSON 示例：

```
TAKEOFF        {"action":"TAKEOFF","params":{"altitude":6.0}}
LAND           {"action":"LAND","params":{}}
HOVER          {"action":"HOVER","params":{"duration":5.0}}
MOVE_VELOCITY  {"action":"MOVE_VELOCITY","params":{"vx":2,"vy":0,"vz":0,"yaw_rate":0,"duration":3}}
MOVE_REL       {"action":"MOVE_REL","params":{"dx":5,"dy":0,"dz":0,"duration":2.5}}
GOTO_NED       {"action":"GOTO_NED","params":{"x":10,"y":5,"altitude":6}}
ORBIT          {"action":"ORBIT","params":{"cx":0,"cy":0,"radius":5,"speed":2,"duration":30}}
YAW_TO         {"action":"YAW_TO","params":{"angle":90}}
RTL            {"action":"RTL","params":{}}
EMERGENCY_STOP {"action":"EMERGENCY_STOP","params":{}}
SET_SPEED      {"action":"SET_SPEED","params":{"speed":3.0}}
FIND_AND_GOTO  {"action":"FIND_AND_GOTO","params":{"query":"person wearing yellow clothes"}}
```

对视觉搜索动作额外补充自然语言说明，约定 `query` 必须使用英文描述目标外观特征。

**② 坐标轴方向约束区**：明确区分机体坐标系（`MOVE_VELOCITY`/`MOVE_REL`：vx=前进，vy=右移，vz 上升为**负**）与 NED 世界坐标系（`GOTO_NED`：x=北，y=东），并用"错方向等于撞机"的强警示措辞强化约束。

**③ 安全约束区**：动态注入 `max_altitude`（默认 120 m）和 `max_speed`（默认 15 m/s）参数值。

**④ 遥测状态区**：运行时注入当前武装状态（ARMED/DISARMED）、飞行阶段（GROUND/HOVERING/MOVING 等）、NED 位置（x/y 米，高度米）、速度（vx/vy/vz m/s）、航向角（°）、当前执行指令名称。使 LLM 能感知无人机实时状态，从而生成上下文适配的指令序列。

**⑤ 输出规则区**：严格限定单步/多步输出格式，禁止任何解释性文字，多步计划以 `{"plan":[...]}` 格式输出，系统顺序执行，每步完成后再执行下一步。

## 4.3 & 4.4 视觉语义识别与几何 Grounding 实现

### 4.3.1 感知链闭环——YOLO-World 动态 Prompt 检测

检测节点 `yolo_world_detector.py` 实现了如下感知闭环：

**模型初始化**：节点启动时调用 `_load_model()`，通过 mmdet 的 `init_detector()` API 加载 YOLO-World v2-S 模型（配置文件 `yolo_world_v2_s_vlpan_bn_2e-3_100e_4x8gpus_...py`，权重 `yolo_world_v2_s_stage1.pth`），优先加载至 `cuda:0`，不可用则降级至 CPU。本地 CLIP tokenizer 若存在（`/home/hw/YOLO-World/clip_tokenizer/`）则直接使用，避免网络依赖。

**动态 Prompt 响应**：节点订阅 `/uav/target_query`（`std_msgs/String`），回调函数 `_on_prompt` 实时更新内部 `self._prompt` 字段。当 LLM 决策层发布 `"person wearing yellow jacket"` 时，检测器在下一推理轮次即切换为对该目标的搜索。

**异步推理机制**：10 Hz 轮询定时器 `_poll_inference` 检查是否有新帧且距上次推理超过 `min_inference_interval_sec`（默认 0.5 s，launch 文件中配置为 0.3 s）。满足条件时启动 daemon 线程执行 `_infer_and_publish`，不阻塞 ROS spin 线程。

**推理核心**（`_run_yolo`，第 299–321 行）：将 prompt 标签转化为 `[[lbl1], [lbl2], ..., [' ']]` 格式（YOLO-World 多类文本输入格式），经 mmengine `Compose` pipeline 预处理后在 `torch.no_grad()` 上下文内调用 `model.test_step(batch)`，按 `score_thr`（默认 0.25）过滤并保留最多 `max_dets`（默认 20）个检测结果。

**输出格式**：发布至 `/uav/detections_2d`（`std_msgs/String`，JSON），包含字段：`prompt`、`image_stamp`、`frame_id`、`inference_ms`、`score_thr`、`detections[{label, score, bbox:{x_min, y_min, x_max, y_max}, stamp, frame_id}]`。

### 4.3.2 逆投影数学实现

几何 Grounding 节点 `target_grounding_node.py` 实现从像素坐标到相机系三维点的逆投影（第 110–205 行）：

**内参获取**：订阅 `sensor_msgs/CameraInfo`，从 $3 \times 3$ 内参矩阵 $K$（行主序）提取：

$$f_x = K[0], \quad f_y = K[4], \quad c_x = K[2], \quad c_y = K[5]$$

**深度采样**：在检测框区域 $[x_1, y_1, x_2, y_2]$ 内以步长 `stride=4` 稀疏采样深度图（`DepthPlanar`，AirSim 输出为 `32FC1` 格式，单位：米），过滤 NaN/Inf 及范围外值（`depth_min=0.1 m`，`depth_max=50.0 m`），取有效像素的**中位数**作为目标深度 $d$（抗噪声比均值更鲁棒）：

$$d = \text{median}\left(\{ \text{depth}[y, x] \mid x_1 \le x < x_2,\; y_1 \le y < y_2,\; 0.1 \le \text{depth} \le 50.0 \}\right)$$

**逆投影公式**：取检测框中心像素 $u = (x_1 + x_2)/2$，$v = (y_1 + y_2)/2$，反投影至相机光学坐标系（x=右，y=下，z=前）：

$$x_{\text{cam}} = \frac{(u - c_x) \cdot d}{f_x}, \quad y_{\text{cam}} = \frac{(v - c_y) \cdot d}{f_y}, \quad z_{\text{cam}} = d$$

输出 JSON 包含完整字段：`{label, score, u, v, depth_m, x_cam, y_cam, z_cam, stamp, frame_id}`，发布至 `/uav/semantic_targets_camera`。

### 4.4.1 坐标系链式变换

`semantic_target_tf_node.py` 实现三阶段链式变换（无需 tf2 动态查找，全部在节点内完成矩阵运算）：

**阶段一：相机光学系 → 机体 NED 系（静态外参）**

系统默认前置平视摄像头安装，外参旋转矩阵定义为（第 113–117 行）：

$$\mathbf{R}_{\text{cam}\to\text{body}} = \begin{bmatrix} 0 & 0 & 1 \\ 1 & 0 & 0 \\ 0 & 1 & 0 \end{bmatrix}$$

即 $x_{\text{body}} = z_{\text{cam}}$（前向），$y_{\text{body}} = x_{\text{cam}}$（右向），$z_{\text{body}} = y_{\text{cam}}$（下向）。可通过 `cam_to_body_rpy_deg` 参数叠加安装角修正（ZYX 欧拉角旋转 `_rpy_to_rotation_matrix`，第 80–100 行）。平移偏置通过 `cam_body_offset_m` 参数配置（默认 `[0,0,0]`）：

$$\mathbf{p}_{\text{body}} = \mathbf{R}_{\text{cam}\to\text{body}} \cdot \mathbf{p}_{\text{cam}} + \mathbf{t}_{\text{cam in body}}$$

**阶段二：机体 NED 系 → 世界 ENU 系（动态位姿）**

里程计话题 `/airsim_node/PX4/odom_local_ned` 提供四元数姿态 $\mathbf{q} = [w, x, y, z]$，通过 `_quat_to_matrix()` 转换为旋转矩阵（第 311–318 行）：

$$\mathbf{R}(\mathbf{q}) = \begin{bmatrix} 1-2(y^2+z^2) & 2(xy-zw) & 2(xz+yw) \\ 2(xy+zw) & 1-2(x^2+z^2) & 2(yz-xw) \\ 2(xz-yw) & 2(yz+xw) & 1-2(x^2+y^2) \end{bmatrix}$$

由于 AirSim 里程计为 NED 坐标系，需乘以 NED→ENU 转换矩阵（第 107–111 行）：

$$\mathbf{R}_{\text{NED}\to\text{ENU}} = \begin{bmatrix} 0 & 1 & 0 \\ 1 & 0 & 0 \\ 0 & 0 & -1 \end{bmatrix}$$

则机体→世界旋转为：

$$\mathbf{R}_{\text{body}\to\text{world}} = \mathbf{R}_{\text{NED}\to\text{ENU}} \cdot \mathbf{R}(\mathbf{q})$$

世界系平移：$\mathbf{t}_{\text{body in world}} = \mathbf{R}_{\text{NED}\to\text{ENU}} \cdot \mathbf{p}_{\text{odom}}$

**阶段三：完整变换**

$$\mathbf{p}_{\text{world}} = \mathbf{R}_{\text{body}\to\text{world}} \cdot \mathbf{p}_{\text{body}} + \mathbf{t}_{\text{body in world}}$$

输出 ENU 世界坐标系坐标，发布至 `/uav/semantic_targets_world`，同时发布 `visualization_msgs/Marker`（红色球体，半径 1 m，3 秒自动消失）供 RViz 实时可视化。

**ENU → NED 最终转换**（在 `text_command_bridge.py` 第 777–779 行执行）：

$$x_{\text{NED}} = y_{\text{ENU}}, \quad y_{\text{NED}} = x_{\text{ENU}}$$

以匹配 `GOTO_NED` 的 $x=\text{North}$，$y=\text{East}$ 约定，无人机飞行高度保持当前高度（`max(2.0, -z_ned_current)`），防止飞入地面。

## 4.5 & 4.6 状态估计与规划接入

### 4.5.1 位姿源驱动——仿真阶段里程计替代

当前 Phase 2 阶段，系统以 AirSim 提供的里程计替代目标阶段的 VINS-Fusion 视觉惯性里程计。具体体现在 `semantic_target_tf_node.py` 的 `odom_topic` 参数默认值（第 128 行）：

```python
self.declare_parameter('odom_topic', '/airsim_node/PX4/odom_local_ned')
```

里程计新鲜度门限为 `max_odom_age_sec=1.0 s`，若超时则拒绝处理当前帧目标（防止用过期位姿计算出错误的世界坐标）。

切换至真机时，只需将 `odom_topic` 参数修改为 `/vins/odometry`，架构其余部分无需改动——这是分层解耦设计的体现（`mapping_config.yaml` 第 20–24 行，规划层统一使用 world/ENU 坐标系，对接 PX4 执行层时在桥接层处理 ENU/NED 转换）。

`text_command_bridge.py` 同时订阅 `/fmu/out/vehicle_local_position`（`VehicleLocalPosition`，uORB 话题，通过 Micro-XRCE-DDS 透传），提供 GOTO_NED 控制器所需的实时 $x$、$y$、$z$、$v_x$、$v_y$、$v_z$、`heading` 字段，以及武装状态。

### 4.6.1 EGO-Planner 集成配置

规划器集成通过 `mapping_config.yaml` 定义 topic 映射关系，其核心配置如下：

| 参数类别 | 配置话题 / 值 | 说明 |
|---------|-------------|------|
| 目标点输入 | `/uav/target_goal` → `/goal_pose` | `PoseStamped`，由 `text_command_bridge` 或 `semantic_target_tf_node` 发布 |
| 里程计输入 | `/vins/odometry` → `odom_world` + `grid_map/odom` | VINS 位姿作为规划状态输入（仿真替换为 AirSim） |
| 点云地图输入 | `/uav/camera/points` → `grid_map/cloud` | `PointCloud2`，AirSim 深度点云占据栅格 |
| 规划轨迹输出 | `/uav/ego_planner/bspline` → `ego_bspline_to_twist_relay` | `traj_utils/Bspline` B 样条轨迹 |
| 速度执行输出 | `/uav/planner_cmd_vel_stamped` → `/hw_insight/keyboard_velocity` | `TwistStamped` 经 `planner_velocity_bridge` 中继 |
| 坐标系 | world/ENU（规划层）；NED（执行层） | 桥接层负责 ENU/NED 转换 |

### 4.6.2 指令转换逻辑——planner_velocity_bridge

`planner_velocity_bridge.py` 是规划层与执行层之间的适配器（`create_timer(0.05, ...)`，20 Hz 中继）：

**双接口订阅**：同时订阅 `TwistStamped`（优先，`prefer_stamped=True`）和 `Twist`（兼容第三方规划器）。

**超时保护**：若规划流中断（指令年龄 > `command_timeout_sec=0.35 s`），发布**一次**全零指令（悬停刹车）后转为静默，避免持续发送过期速度导致无人机失控漂移。

### 4.7.2 Offboard 状态机——解锁窗口的时间冗余设计

`move_velocity.py` 实现完整的 Offboard 起飞状态机（`timer_callback`，第 158–224 行），以 **10 Hz** 周期运行：

**安全门机制**：系统启动后进入静默期（`flight_enabled=False`），对 PX4 保持完全静默，防止 ROS 节点启动瞬间意外触发武装。仅当 `hw_velocity.z < ARM_TRIGGER_THRESHOLD(-5.0 m/s)` 时，`flight_enabled` 置 `True` 并记录日志，此后持续发送 Offboard 心跳直至无人机降落后重置。

**ARM 阶段时间冗余**（核心设计，第 42–43 行）：

```python
ARM_TRIGGER_Z   = -6.0   # m/s，NED z 轴 — 触发 Offboard 的上升速度指令
ARM_TRIGGER_SEC = 2.5    # s   — WSL2 时间同步抖动补偿窗口
```

起飞指令到达后，`TextCommandBridge` 记录起飞开始时间戳 `takeoff_start_ns`。在 `_in_arm_phase()` 返回 `True` 的 **2.5 秒窗口内**，持续向 PX4 发送 `z=-6.0 m/s` 的强上升指令（而非目标高度的 P 控制指令），保证 PX4 在 WSL2 时间同步抖动（可达数百毫秒）的情况下仍能稳定完成 `engage_offboard_mode()` → `arm()` 序列。超过 2.5 秒后切换为高度 P 控制：

$$v_z = \text{clamp}\left(K_p \cdot (z_{\text{target}} - z_{\text{current}}),\; -v_{z,\max},\; +v_{z,\max}\right), \quad K_p = 0.8,\; v_{z,\max} = 3.0\ \text{m/s}$$

高度到达容差 `altitude_tolerance=0.35 m`，到达后速度归零进入悬停。

**降落保护**：检测到 `nav_state==AUTO_LAND` 且 `distance_sensor.range < 5 m` 时自动触发 `land()` 命令（防止 Offboard 指令与自动降落冲突）；若在降落中收到强上升指令（`z < -5.0`），切回 Offboard 中止降落。

### 算法 4-1：鲁棒 JSON 提取算法（五步容错解析）

```
Algorithm RobustJSONExtract(raw_text):
  Input:  raw_text — LLM 原始输出字符串
                     （可能含 Markdown 代码块、<think> 推理块、冗余自然语言）
  Output: parsed_obj — Python dict，或 None（全部策略均失败）

  // Step 1: 预处理
  text ← StripFences(raw_text)
      // 移除 ```json...``` 标记
      // 移除 <think>...</think> 推理块（独立持久化至日志）

  // Step 2: S1 策略 — 直接解析
  try:
    obj ← json.loads(text)
    return obj
  except JSONDecodeError:
    pass

  // Step 3: S2 策略 — 括号平衡候选集
  candidates ← BalancedBraceCandidates(text)
      // 线性扫描，记录所有顶层 { 的起止位置（正确处理嵌套）
      // 按候选串长度降序排列
  for each cand in candidates:
    try:
      obj ← json.loads(cand)
      if isinstance(obj, dict) AND ("action" in obj OR "plan" in obj):
        return obj
    except JSONDecodeError:
      continue

  // Step 4: S3 策略 — 正则回退
  patterns ← [
    r'\{[^{}]*"action"\s*:\s*"[^"]+?"[^{}]*\}',     // 单步指令
    r'\{\s*"plan"\s*:\s*\[[\s\S]*?\]\s*\}',           // 多步计划
  ]
  for each pat in patterns:
    match ← regex.search(pat, text, DOTALL)
    if match:
      try:
        obj ← json.loads(match.group())
        if isinstance(obj, dict): return obj
      except JSONDecodeError: continue

  // Step 5: 安全兜底
  return None  // 调用方收到 None 后发布 HOVER 兜底指令
```

### 算法 4-2：深度逆投影与坐标链式变换

```
Algorithm SemanticGrounding(det, depth_map, K, R_cam2body, t_cam,
                             R_body2world, t_body):
  Input:
    det          — 检测结果 {bbox: {x1, y1, x2, y2}}
    depth_map    — H×W float32 深度图（米，DepthPlanar 格式）
    K            — 3×3 相机内参矩阵（fx, fy, cx, cy 从 K 提取）
    R_cam2body   — 相机→机体 3×3 旋转矩阵（静态外参）
    t_cam        — 相机在机体系的平移偏置 [3×1]
    R_body2world — 机体→世界 3×3 旋转矩阵（由四元数里程计实时计算）
    t_body       — 机体在世界系的位移 [3×1]
  Output: p_world — 目标在世界 ENU 坐标系的三维坐标，或 None

  // 阶段 1: 采样中位数深度
  region ← depth_map[y1:y2:stride=4, x1:x2:stride=4]
  valid  ← { v ∈ region | 0.1 ≤ v ≤ 50.0 AND isfinite(v) }
  if |valid| = 0: return None
  d ← median(valid)

  // 阶段 2: 逆投影至相机光学坐标系 (x=右, y=下, z=前)
  u ← (x1 + x2) / 2.0;  v ← (y1 + y2) / 2.0
  fx ← K[0,0];  fy ← K[1,1];  cx ← K[0,2];  cy ← K[1,2]
  p_cam ← [ (u - cx)·d / fx,
             (v - cy)·d / fy,
             d             ]

  // 阶段 3: camera_optical → body_NED（静态外参）
  p_body ← R_cam2body · p_cam + t_cam
  // 默认 R_cam2body = [[0,0,1],[1,0,0],[0,1,0]]
  // 即: x_body=z_cam(前向), y_body=x_cam(右向), z_body=y_cam(下向)

  // 阶段 4: body_NED → world_ENU（动态位姿）
  // R_body2world = R_NED2ENU · R(quaternion)
  // R_NED2ENU = [[0,1,0],[1,0,0],[0,0,-1]]
  p_world ← R_body2world · p_body + t_body
  // 输出为 ENU 坐标: [East, North, Up]

  // 阶段 5: ENU → NED（在 TextCommandBridge 中执行，用于 GOTO_NED）
  x_NED ← p_world[1]  // North = ENU-Y
  y_NED ← p_world[0]  // East  = ENU-X
  alt   ← max(2.0, current_drone_altitude)  // 保持当前飞行高度

  return (x_NED, y_NED, alt)
```

### 算法 4-3：GOTO_NED 比例导航控制器

```
Algorithm GotoNEDController(target, pos):
  Input:
    target = (tx, ty, tz_ned) — NED 目标点
    pos    = (px, py, pz)     — 当前 NED 位置（来自 VehicleLocalPosition）
  Constants:
    GOTO_KP        = 0.8      — 比例增益
    GOTO_TOLERANCE = 0.5 m   — 到达容差半径
    v_max_h        = 4.0 m/s  — 水平速度上限
    v_max_z        = 2.5 m/s  — 垂直速度上限
    v_abs_max      = 15.0 m/s — 硬件安全截断
  Output: velocity command (vx, vy, vz) 或 HOVER 信号

  ex ← tx - px;  ey ← ty - py;  ez ← tz_ned - pz
  dist_xy ← sqrt(ex² + ey²)
  dist_3d ← sqrt(ex² + ey² + ez²)

  if dist_3d ≤ GOTO_TOLERANCE:
    clear goto_target
    publish GOTO_NED_ARRIVED event
    return (0, 0, 0)

  h_speed ← min(v_max_h, GOTO_KP · dist_xy)
  if dist_xy > 0.01:
    vx ← h_speed · (ex / dist_xy)
    vy ← h_speed · (ey / dist_xy)
  else:
    vx ← vy ← 0

  vz ← clamp(GOTO_KP · ez, -v_max_z, +v_max_z)
  return (clamp(vx, -v_abs_max, +v_abs_max),
          clamp(vy, -v_abs_max, +v_abs_max),
          vz)
```

### 算法 4-4：ORBIT 切向+修正速度控制器

```
Algorithm OrbitController(center, radius, speed, angle, pos, dt):
  Input:
    center = (cx, cy) — 圆心 NED 坐标
    radius            — 轨道半径（m）
    speed             — 切向速度（m/s）
    angle             — 当前角位置（rad），每 tick 累积
    pos               — 当前 NED 位置
    dt = 0.1 s        — 控制周期
  Constants:
    ORBIT_KP = 1.0    — 半径修正增益
  Output: velocity command (vx, vy, vz)

  // 角位置推进
  ω ← speed / radius
  angle ← angle + ω · dt

  // 期望位置（圆周上）
  desired_x ← cx + radius · cos(angle)
  desired_y ← cy + radius · sin(angle)

  // 切向速度（垂直于半径方向）
  tang_vx ← -speed · sin(angle)
  tang_vy ←  speed · cos(angle)

  // 修正速度（拉回圆周）
  corr_vx ← ORBIT_KP · (desired_x - pos.x)
  corr_vy ← ORBIT_KP · (desired_y - pos.y)

  // 高度 P 控制
  vz ← clamp(K_alt · (orbit_z_ned - pos.z), -v_max_z, +v_max_z)

  vx ← clamp(tang_vx + corr_vx, -15, +15)
  vy ← clamp(tang_vy + corr_vy, -15, +15)
  return (vx, vy, vz)
```

## 审计结论

当前 Phase 2 代码库在三个核心技术维度均存在可直接引用的学术价值：

1. **视觉感知链**（YOLO-World → 中位数深度逆投影 → 三阶段 TF 变换）：数学推导完整，代码实现与公式一一对应，具备"感知 → 定位 → 转系"的完整闭环。

2. **LLM 任务理解层**（鲁棒 JSON 提取、双后端推理、12 动作原语 Schema）：五步容错解析算法对生成式模型输出的随机性具有工程针对性，与"决策链路确定性保障"这一研究贡献直接对应。

3. **控制执行层**（Offboard 状态机、ARM 2.5 s 冗余窗口、比例导航控制器）：WSL2 时间同步抖动的工程补偿设计是论文叙述中"系统实现难点与解决方案"的典型素材。

**待补充**：EGO-Planner 规划器的具体超参数（栅格分辨率、B 样条优化权重 $\lambda_{\text{smooth}}$、$\lambda_{\text{feas}}$）需在 EGO-Planner 对应配置文件中进一步参数化后方可精确引用，建议在 Phase 3 联调阶段补充至本报告附录。
